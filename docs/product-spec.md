# EVOworkflow v0.2 产品规格

## 定义

EVOworkflow 是面向长期项目的一套人工控制、以仓库为中心、AI 辅助、证据驱动的软件工程工作流。

```text
人工控制 WHAT、WHY、APPROVAL 和 ACCEPTANCE。
Agent 调查事实并执行已授权工作。
仓库保存持久知识。
证据决定是否可以完成。
```

只有当意图、边界、验收和停止条件已经批准时，EVOworkflow 才可以自动化执行工作；它不会自动化处理模糊意图。

## 产品目标

- 让非专业人员在获得相关工程建议的同时保持控制权。
- 让真实仓库，而不是通用框架知识，成为工作权威。
- 在新写实现前优先使用已有能力、框架设施、维护中的库和成熟开源方案。
- 保存当前事实、持久 Decision、活动工作、历史证据和恢复上下文，不把仓库变成聊天记录。
- 围绕稳定模块约定和可验证的垂直 Slice 控制改动范围。
- 在有充分依据时，把重复故障转化为约定，再转化为机器门禁。
- 在明确批准后支持有边界、顺序执行的长期工作。

## 长期非目标

- 多 Agent 并行执行。
- 云控制面板、仪表板、中央数据库、向量数据库或插件市场。
- 自动产品、业务、安全或重大架构 Decision。
- 自动 commit、merge、release、生产部署或 Change 完成。
- 把某一种架构强加给所有受管理仓库。
- 与当前 Change 无关的穷尽式清单。

## 必须具备的能力

1. 新 Agent 无需历史聊天即可恢复项目上下文。
2. Brownfield 初始化识别真实项目约定并报告未知项。
3. Greenfield 指导在自建实现前比较成熟基础方案。
4. Standard Feature 可以经过 Grill、Plan、Implement、Verify、Review 和 Finish。
5. 需求变更保存明确的旧到新 Delta，并更新受影响的文档。
6. Bug 工作记录复现证据、根因、回归检查和真实入口状态。
7. `ask-evo` 报告当前状态和下一个人工控制动作。
8. `ask-evo-architect` 根据仓库证据提供架构建议。
9. `evo-engineering` 只加载与当前 Change 触发条件相关的工程启发。
10. Goal 至少可以顺序执行五个已批准 Slice。
11. 需要未批准 Decision 时，Goal 必须停止。
12. Goal 结束为 `READY_FOR_REVIEW`；只有 `evo-finish` 可以完成 Change。
13. Finish 检查已批准意图、Decision、代码、测试、证据和当前文档是否收敛。
14. `evo-recover` 无需聊天历史即可恢复当前目标、阶段、已完成工作、待办工作、阻塞和下一步。
15. 项目地图拒绝同一个长期事实拥有多个主权威。
16. Working Context 按任务路由仓库路径与选择理由，且不把源代码或文档正文复制成第二份知识。
17. Consistency 分析报告现有机制、命名和实际影响范围的候选漂移，供人工 Review 使用。
18. Requirement Delta、Bug 和 Recovery 保留中断、变化与未知项，不能静默覆盖批准或把未知改成已验证。
19. 二期评估能够比较固定 RuoYi 与独立 FastAPI + Ant Design Pro 仓库，证明框架习惯不会跨项目泄漏。

## v0.2 仍不做什么

- 自动选择或切换框架、响应协议、权限机制或重大架构。
- 真实 RuoYi 启动、MySQL、浏览器、Agent、部署或生产回滚。

## 工程默认值

- 除非有测量结果支持其他架构，否则先使用模块化单体。
- 约定严格，方法灵活。
- 事实由 Agent 调查；Decision 由人工决定。
- 当前事实与历史记录分开保存。
- 频繁运行聚焦验证，在接近完成时运行广泛验证。
- 复杂度必须值得它带来的维护成本。
